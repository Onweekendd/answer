## 工程化：CI/CD 与部署（2026-10-15 完成）

### 定位

不单独写成一个项目，而是作为「买不买」项目下的一条"工程化"要点。核心卖点仍然是 AI 和并发；这一条用来证明能把东西从代码一路负责到线上。

### 简历写法

**简洁版（一行）：**

> 搭建 GitHub Actions 持续部署流水线（测试 → 多阶段 Docker 构建 → SSH 部署），部署前自动备份、健康检查失败自动回滚，push 后约 10 分钟上线。

**详细版：**

> - 基于 GitHub Actions 实现 CI/CD：单元测试与仓储测试分别在 SQLite 和 PostgreSQL（dockertest）上运行；多阶段 Docker 构建，前端经 `go:embed` 打进单个二进制，镜像按 commit 号打标签推送到 GHCR；通过 SSH（固定主机指纹）触发服务器部署脚本，部署前自动备份数据库，健康检查失败自动回滚。
> - Docker Compose 编排应用与 PostgreSQL（pgvector），数据库只在内部网络可见；用 dumb-init 作为 PID 1 并 `exec` 启动服务，保证收到 SIGTERM 时优雅退出；cron 每日备份并验证过恢复。
> - 上线过程中定位并修复 PostgreSQL 自增序列未同步导致的主键冲突（迁移中显式写入 ID），补充迁移与回归测试。

数字来源（run 38707255749）：test 约 1.5 分钟，build 约 6 分钟，deploy 约 1 分钟。

### 不要写

- k8s、高可用、蓝绿发布：实际是单机、替换式部署，一追问就露馅。
- "零停机"：容器重建的一两秒网站不可用。
- Docker / GitHub Actions "精通"：写"使用"或直接写做了什么。

### 面试故事

**1. PostgreSQL 序列 bug（最推荐，数据库原理）**

上线后新用户注册报主键冲突。迁移里给管理员和机器人账号显式写了 ID 1 和 2，而 PostgreSQL 的序列不会因为显式写入而前进，下一次 `nextval` 还是 1。

修复：用 `setval(seq, MAX(id)+1, false)` 把序列推过去，写成幂等迁移（v38），并让全新安装路径（`InitDB` 不走迁移，直接把版本号写成最新）也调用它；补了 PG 上的回归测试，并用变异测试确认测试能抓到问题。

可延伸：序列为什么是非事务的；全新安装和升级是两条路径，改数据库时两条都要顾到。

**2. PID 1 与优雅退出（CSAPP 功底）**

容器里第一个进程是 PID 1，内核对它特殊处理：没有注册处理函数的信号会被忽略，所以 `docker stop` 的 SIGTERM 可能没反应，10 秒后被 SIGKILL 强杀。

做法：dumb-init 当 PID 1 转发信号、回收僵尸进程；入口脚本最后一行用 `exec` 让 answer 替换掉 shell，信号直接送到 Go 程序，走 pacman 的 `signal.Notify` → `Stop()` 优雅停机。

**3. 回滚的边界（体现风险意识）**

健康检查失败会自动切回旧镜像，但回滚只回滚代码、不回滚数据库：新版本跑过的迁移不会撤销，所以部署前先备份。

读迁移代码时发现：`answer upgrade` 失败只打印错误，退出码仍是 0；`/healthz` 只看进程活着。结果是迁移失败的部署会被判成功。结论：靠退出码传递结果的链路上，每一环都必须如实上报失败。

> 待办：面试前修掉（`upgradeCmd` 失败时 `os.Exit(1)`，entrypoint 写成 `answer upgrade || exit 1`），这个故事就能从"发现了"变成"修了"。

**4. 排查 CI 连不上服务器（排查方法）**

SSH 主机指纹校验失败。服务器有 RSA / ECDSA / ed25519 三把主机密钥，ssh-action 内部的 Go SSH 库（x/crypto v0.29）优先协商 ECDSA，而配置的是 ed25519 指纹。用同版本的库写了一个只做握手、不认证的小程序复现并确认。

另外两个坑：网页粘贴 Secret 带进不可见字符（改用 `gh secret set`）；`authorized_keys` 末尾缺换行导致两把公钥粘成一行。

### 可能被追问

- **为什么部署逻辑写在服务器的 deploy.sh 里，而不是全写在 workflow 里？** 每一层都能单独手动跑：CI 坏了，在服务器上手敲 `./deploy.sh <tag>` 效果一样；也方便本地测试。
- **镜像为什么用 commit 号打标签，而不是只用 latest？** 可追溯，线上跑的是哪次提交一眼可知；回滚就是把 TAG 改回旧号。
- **为什么不在服务器上构建？** 服务器 2 核 4G、5Mbps，构建慢且占资源；GitHub 的机器构建完推到仓库，服务器只拉取，"门店不做菜"。
- **数据库为什么不暴露端口？** Compose 内部网络里服务名就是主机名，应用通过 `db:5432` 访问，公网无需也不应该能连。
- **测试为什么分 SQLite 和 PG？** 上游仓储测试只在 SQLite 上维护过，放到 PG 上有一批上游兼容问题；我们自己依赖 PG 行为的测试（行锁、并发投票、事务回滚、序列）单独在 PG 上跑。

## 浏览器 Agent：Chrome 插件 + Go Hub（2026-10-16 完成 P1 和第一个里程碑）

### 定位

这是「买不买」里 AI 那条线的"眼睛和手"：Agent 通过用户自己的浏览器看页面、点按钮。简历上和需求 4 的 Agent 写在一起，卖点是**并发（反向 RPC）**和**给大模型的页面压缩**。

### 简历写法

**简洁版（一行）：**

> 用 Chrome 插件（MV3）+ Go WebSocket Hub 实现浏览器 Agent 的执行层：在一条长连接上做反向 RPC 的请求/响应配对，页面快照压缩到原始 HTML 的 0.3%～0.4%，供大模型按编号操作页面。

**详细版：**

> - 设计 Go ⇄ 浏览器插件的反向 RPC：插件主动连接、Go 下发命令，按命令 id 配对乱序返回的结果；单读者 goroutine + 按连接隔离的 pending 表 + 容量为 1 的 channel，保证超时、断线、重连时不阻塞、不串号；50 路并发乱序回复的测试与 `-race` 验证。
> - 研究 browser-use 的页面压缩实现及其 git 历史中的问题，设计"可交互元素按键图"快照：去掉 href、嵌套链接合并为一行、属性白名单、隐私脱敏统一出口；实测淘宝首页 84 万字 → 3380 字，B 站首页 118 万字 → 3383 字；淘宝搜索页 47 个商品约 8000 字（browser-use 同一页面约 2.4 万字、40 个商品）。
> - 插件内核不含任何站点规则，content script 按需注入；本地连接校验 Origin 与 token，日志不记录网址、标题和页面内容。

数字来源：`docs/page-snapshot-design.md` §9 实测记录。

### 不要写

- "自研浏览器自动化框架""支持所有网站"：是个人工具，已知还有轮播重复、卡片被拆成多行等问题（P2）。
- "绕过反爬""规避检测"：没有做，也不该做；遇到验证码要停下来交给人。
- "高并发"：单用户、单连接，并发体现在一条连接上多个调用的正确性，不是吞吐量。

### 面试故事

**1. 一条 WebSocket 上的反向 RPC（最推荐，并发）**

方向是反的：浏览器插件不能监听端口，只能由插件连 Go，但命令由 Go 发。HTTP 自带的一问一答配对在这里没有了，同一条连接上多个命令的结果会乱序回来。

做法：每条命令带 id，pending 表里放一个容量为 1 的 channel。只有一个 goroutine 读连接（库的要求），它在锁里"取出并删除"表项再发送，所以每个 channel 只会被发一次，容量 1 保证发送永远不阻塞；调用方超时走了，结果放进缓冲区就被丢弃，不会拖死整条连接。断线时 `failAll` 通知所有等待者，并设置 `closed`；`closed` 的检查和登记在同一把锁里，避免"刚清理完表又有新调用登记进来、永远没人通知"。pending 表跟着连接走，重连时旧连接只清理自己的调用。

踩过的坑：第一版在锁外读 map，Go 运行时直接 `fatal error: concurrent map read and map write`；还有从表里重新查 channel，结果回得太快时查到 nil channel 永远阻塞。用 50 路并发、乱序回复的测试复现，Windows 没有 gcc，在 Docker 的 Linux 容器里跑 `-race`。

可延伸：为什么不用容量 0；为什么断线返回哨兵错误 `ErrDisconnected` 而不是 `CommandError`（调用方处理方式不同）；断线时 click 不能盲目重试（非幂等）。

**2. 页面压缩：用数据决定规则（AI 工程）**

第一版快照里 href 占了 81.6% 的字数。读 browser-use 的实现和 git 历史，整理出它踩过的坑（URL 正则误伤、被遮挡的文字泄漏、密码框的值），再在真实页面上逐条量。图标字体的私用区字符、价格小数被拆开这些问题，都是看了实测输出才发现的。

原则是"先有数据再加规则"：轮播图重复在淘宝和 B 站都出现，说明该在通用内核里解决；只有一个网站有的结构才考虑写站点策略。

**3. 通用内核 + 按需注入 + 本地连接的安全（设计取舍）**

插件不认识任何网站。content script 不在 manifest 里自动注入，而是 Go 第一次操作某个页面时，收到"没有接收方"再用 `chrome.scripting` 注入并重试；用一张 `Map<tabId, Promise>` 保证并发命令只注入一次（注入两份会让一次 click 执行两遍）。

Hub 只监听 127.0.0.1，但任何网页都能连本机端口，所以握手时先挡掉非 `chrome-extension://` 的 Origin，再在第一条消息里用固定时间比较校验 token。

**4. MV3 service worker 会睡着（平台理解）**

background 空闲约 30 秒会被关掉。应对：连上后每 20 秒发 ping 保活；`chrome.alarms` 每 30 秒兜底唤醒；所有事件监听在顶层同步注册；重连用一个共享的 `opening` Promise 避免同时建两条连接。

### 可能被追问

- **为什么不用 Playwright / CDP 直接开一个浏览器？** 要用用户自己的浏览器和登录状态，也不想另开一个带自动化特征的浏览器；browser-use 默认是另起一个 Chrome、临时用户目录。
- **为什么用 WebSocket，不用 HTTP 轮询或 Native Messaging？** 命令要由 Go 主动推给插件，长连接最直接；Native Messaging 要装本地宿主程序，而 Hub 本来就在 Go 进程里。
- **为什么同一时间只保留一个插件连接？** 单用户；tabId 只在一个浏览器内唯一，多连接要改成 (clientId, tabId) 寻址，connection 不用改，只改 Hub。
- **navigate 怎么知道页面加载完了？** 先注册 `tabs.onUpdated` 监听再发起跳转（事件错过就没了），只认 `changeInfo.status === "complete"`（`tab.status` 会被旧页面的事件骗到），超时和成功两条路都移除监听。
- **快照里为什么没有链接地址？** 模型通过编号操作元素，用不到地址；要地址时单独提供 `link(编号)`。
- **Hub 为什么是单独的进程（`answer browser`），不挂进后端（`answer run`）？** 技术上不难：`*browser.Hub` 本身就实现了后端要的 `Browser` 接口（`Call` / `Connected`），挂进去就是直接函数调用。分开有三个理由：
  - 开发时 air 每次保存都重启后端，Hub 在里面的话插件的 WebSocket 每次都断、要等重连；分开以后后端怎么重启，插件连接都不受影响。
  - 网络边界：线上后端对公网开放，Hub 只绑服务器的 `127.0.0.1:8765`，本机插件走 SSH 隧道连过去。挂进后端就得对公网开放 `wss://…/agent`，要 TLS 和按用户的 token，这是之后「每用户配对浏览器」的需求。
  - Hub 里存的是插件的**活连接**，只在一个进程的内存里。以后后端多实例，Hub 必须是大家共用的一处，单独进程天然就是这个形状。

  代价是多一跳 HTTP，以及启动要两条命令（用 `script/dev.sh` 一条命令起两个、Ctrl+C 一起停）。后端里留着 `noBrowser`：没配 Hub 时 Agent 降级成直接回答，不报错。
- **后端怎么找到 Hub，token 怎么校验？** 后端读 `BROWSER_HUB_URL` 和 `BROWSER_HUB_TOKEN`，通过 Hub 的 `/api/browser/` HTTP 接口调用（带 `Authorization: Bearer`）；插件连 `/agent` 时在第一条消息里带同一个 token，Hub 用固定时间比较校验。同一个 token 要在三处一致：本地 `.env`、插件 popup、（线上用另一个）服务器的 `deploy/.env`。细节：`.env` 是 Windows 换行，读的时候要去掉 `\r`，不然 token 末尾多一个不可见字符，两边比较永远不相等。
