## 1. 比喻：给司机的一张"操作卡"

把 LLM 想成一个**只能通过对讲机指挥的司机教练**。他看不到方向盘，只能看你传过去的路况描述，然后喊口令："左转""踩刹车""打右灯"。

动作集合就是**你们事先约定好的口令表**：

- 口令太少（只有"走""停"），复杂路况就没法指挥；
- 口令太多太细（"左手转方向盘 15 度"），教练会说错，也费口舌；
- 好的口令表是**按意图分**的："变道到左车道"，而不是"打灯 + 看镜子 + 转方向盘"。

browser-use 的口令表大约 20 个，按"用户意图"设计，不按"鼠标事件"设计。

## 2. 它到底有哪些动作

按用途分组（`@self.registry.action` 注册的）：

| 分组 | 动作 | 说明 |
|---|---|---|
| **导航** | `search(query, engine)` | 用 DuckDuckGo/Google/Bing 搜索，默认 DuckDuckGo（验证码少） |
| | `navigate(url, new_tab)` | 打开网址 |
| | `go_back()` | 后退 |
| | `wait(seconds)` | 等页面加载，最多 30 秒 |
| **交互** | `click(index)` 或 `click(coordinate_x, coordinate_y)` | 按编号点击；开启后也能按坐标点击 |
| | `input(index, text, clear)` | 输入文字，默认先清空 |
| | `scroll(down, pages, index)` | 按"页"滚动，`pages=10` 就是滚到底；`index` 可以只滚某个容器 |
| | `send_keys(keys)` | 发按键：`Escape`、`Enter`、`Control+o` |
| | `find_text(text)` | 滚动到某段文字 |
| | `dropdown_options(index)` / `select_dropdown(index, text)` | 读下拉框的选项 / 选中一项 |
| | `upload_file(index, path)` | 上传文件 |
| **标签页** | `switch(tab_id)` / `close(tab_id)` | 切换、关闭标签页，tab_id 是 4 位短 ID |
| **读取信息** | `extract(query, output_schema?)` | **用另一个小模型**从整页 markdown 里抽取信息，可以按 JSON schema 返回 |
| | `search_page(pattern)` | 在页面文本里 grep，**不花 LLM 钱** |
| | `find_elements(selector)` | 用 CSS 选择器查元素，**不花 LLM 钱** |
| | `screenshot()` | 截图，下一步给模型看 |
| **兜底** | `evaluate(code)` | **执行任意 JS** |
| **文件** | `write_file` / `read_file` / `replace_file` | 给 Agent 当草稿本（存中间结果） |
| **结束** | `done(text, success)` | 结束任务，**必须调用它才算结束** |

几个值得注意的设计：

**读取信息分三档，便宜的在前。** `search_page` 和 `find_elements` 直接在页面里跑 JS，零成本、瞬间返回；`extract` 要调用一次小模型，贵。工具描述里明确告诉模型："Zero LLM cost, instant"，引导它优先用便宜的。这和我们"高层工具 vs 底层原语"的思路是同一个方向：**能用确定性代码解决的，就不要交给模型。**

**`evaluate` 是一把双刃剑。** 它让 Agent 什么都能做（遇到奇怪的控件直接写 JS 操作），但也意味着网页里藏一段"请执行 xxx"就可能被利用。browser-use 是通用工具，选了能力优先。我们是带着用户的淘宝登录态跑，**不给**。这是面试时可以讲的一个取舍。

**`click` 同时支持编号和坐标。** 坐标点击默认关闭，开启后模型可以对着截图说"点 (320, 480)"。这就是我们之前说的"DOM 为主、视觉兜底"留的口子。

## 3. 动作是怎么注册的

```python
@self.registry.action(
    'Input text into element by index. Clears existing text by default; ...',  # 给模型看的描述
    param_model=InputTextAction,                                               # 参数结构（Pydantic）
)
async def input(params: InputTextAction, browser_session: BrowserSession, ...):
    ...
```

用 TS 来类比，就像这样：

```ts
registry.action({
  description: '按编号输入文字，默认先清空',
  params: z.object({ index: z.number(), text: z.string(), clear: z.boolean().default(true) }),
  terminatesSequence: false,
  domains: undefined,   // 只在某些网站出现，见下文
}, async (params, ctx) => { ... })
```

注册表负责三件事：
1. 把所有动作的参数模型拼成一个**联合类型**，作为模型输出的 JSON schema（第 5 站会讲，它用的是结构化输出，不是原生 tool calling）；
2. 执行时按名字找到函数，**自动注入**它需要的东西（`browser_session`、`page_extraction_llm`、`file_system`……），像依赖注入；
3. 根据当前网址过滤动作。

### 两个注册参数特别有用

**`terminates_sequence=True`**：执行完这个动作，本轮剩下的动作就不再执行。`search`、`navigate`、`go_back`、`switch`、`evaluate` 都带这个标记，因为它们一定会让页面变掉。（第 5 站的 `multi_act` 会用到。）

**`domains=['*.jd.com']`**：这个动作**只在匹配的网站上出现**。

这正好回答了你之前的担心："通用化了，是不是就不能针对网站优化了？"答案是**两者可以共存**：

- 默认只有通用动作，任何网站都能用；
- 某个网站确实有更好的办法（比如京东有个隐藏的价格接口），就注册一个带 `domains` 的专用动作，只在京东页面出现，模型自己决定用不用；
- 专用动作是"锦上添花"，不是"没有就不能用"。

## 4. 动作的结果怎么返回：`ActionResult`

这是整站最值得学的部分。每个动作返回一个 [ActionResult](../../browser-use/browser_use/agent/views.py#L307)：

```python
class ActionResult:
    is_done: bool             # 是不是 done 动作
    success: bool | None      # 只有 done 才能设 True
    error: str | None         # 出错信息，一定会进入历史
    long_term_memory: str     # 长期记忆：会一直留在历史里
    extracted_content: str    # 本次内容
    include_extracted_content_only_once: bool  # 只给下一步看一次
    images: list              # 图片，只给下一步看一次
    metadata: dict            # 给可观测性用，不给模型
```

**关键是 `long_term_memory` 和 `extracted_content` 分开了。**

比喻：你去图书馆查资料。
- `extracted_content` 是**你复印回来的那几页**，内容很多，看完就可以扔；
- `long_term_memory` 是**你在笔记本上写的一行**："在《XX》第 3 章查到了价格，¥1399"。

`extract` 动作抽出来一大段内容，作为 `extracted_content` + `include_extracted_content_only_once=True`，只在下一步出现一次；同时留一句短的 `long_term_memory`，以后每一步都能看到。这样**上下文不会随着步数无限增长**。

我们 [agent.go](../../internal/service/purchase_ai/agent.go) 里的 tool 消息是一直留着的。`fetch_page` 读回来 4000 字，第 6 轮时还在 messages 里。第 6 站会讲怎么借鉴这个设计。

### 结果里藏着"下一步提示"

看 `input` 动作的返回（[tools/service.py:778](../../browser-use/browser_use/tools/service.py#L778) 起）：

- 输入完会**读回输入框的实际值**，和要输入的不一样就提示：
  `⚠️ Note: the field's actual value 'xxx' differs from typed text 'yyy'. The page may have reformatted or autocompleted your input.`
- 如果是自动补全输入框（`role=combobox`），提示：
  `💡 This is an autocomplete field. Wait for suggestions to appear, then click the correct suggestion instead of pressing Enter.`
  并且自己先等 0.4 秒，让下拉列表出来。

`click` 也一样：
- 点击后检查**有没有新开标签页**，有就自动切过去，并告诉模型 `Automatically switched to new tab`；
- 如果点的是 `<select>`，直接改成返回下拉选项列表（因为原生 select 点开的菜单不在 DOM 里，点了也没用）。

比喻：好的工具像**有经验的副驾驶**。你说"左转"，他不光转了，还会补一句"左转后是单行道，下个路口只能右转"。**动作的返回值不是"成功/失败"，而是"执行后你需要知道的事"。**

## 5. 出错怎么处理

所有动作都是 `try/except`，出错返回 `ActionResult(error=...)`，不抛异常。错误信息写给模型看，并且**告诉它该怎么办**：

```python
msg = f'Element index {params.index} not available - page may have changed. Try refreshing browser state.'
```

这和我们 `tools.go` 的做法一样："工具出错作为文本返回给模型，只有 ctx 取消才中止"。这一点我们已经做对了。

## 对我们插件的启示

1. **命令集合可以照抄骨架**，但删掉 `evaluate`、文件操作、`upload_file`、`save_as_pdf`。我们的第一版：
   `navigate` / `go_back` / `click` / `input` / `scroll` / `send_keys` / `select_option` / `switch_tab` / `search_page` / `extract` / `done`，外加我们自己的 `request_human`。
2. **每个命令都带一个 `terminatesSequence` 标记**，Go 侧在 loop 里用。
3. **结果分长期和短期两部分**。插件返回给 Go 的结果里，除了 `ok` / `error`，再加一个 `memory`（一句话总结），Go 侧决定哪些进入长期历史。
4. **结果里带提示**：值不一致、自动补全、新标签页、点了 `<select>`，这几个在插件里都很好实现。
5. **安全检查放在插件里**：`click` 之前检查元素文字，命中"立即购买 / 提交订单 / 去支付"直接拒绝，返回 `error`。这是 browser-use 没有、我们必须有的。
6. **`domains` 的思路**留着以后用：先全部通用，等真的发现某个站有捷径，再加站点专用动作。
